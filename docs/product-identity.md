# Product Identity

_最終更新: 2026-04-23_

> Mind → Visual → Behavior の順に定義する。
> Mindが定まらないとVisualの判断基準が生まれず、Visualが定まらないとBehaviorの「なぜそう動くか」が語れない。

---

## Mind Identity（MI）

> **「このプロダクトは何を信じているか」**
> ブランドの魂。すべての意思決定の判断軸になる。

### Purpose（存在意義）

_なぜこのプロダクトは存在するか_

AI開発時代、デザインの主役はFigmaのような視覚ツールからドキュメントに移行する。
開発をAIに委ねるとき、AIが読めるのはコードとドキュメントだけであり、Figmaファイルではない。
StorybookはコードとのDX（開発者体験）に優れるが、既存デザインツールとの接続が弱く、AIコンテキストとして使いにくい。

**私たちはAI開発時代のデザインプロセスそのものを再定義する。**
デザインシステムを「人とAIの両方が読める唯一の情報源（SSOT）」として確立し、
AIが正確にUIを生成・実装できるための新しい基準を提供する。

```
旧プロセス: Designer (Figma) → 手動ハンドオフ → Developer (コード)

新プロセス: Designer → Design System Hub (人もAIも読めるSSoT)
                                  ↓
                          AI が Hub を読んでコードを生成
                                  ↓
                          デザインシステムと一貫したコード
```

### Belief（信念）

_このプロダクトが正しいと信じていること_

1. **デザインシステムはAIが読める形式で存在すべきだ**
   Figmaファイルは人間の目には美しいが、AIのコンテキストとしては機能しない。構造化されたドキュメントこそが次世代の設計図。

2. **デザインツールへの依存は技術的負債になる**
   特定プラットフォームにロックインされたデザインシステムは、ツールが廃れたとき一緒に失われる。プラットフォーム中立な形式が長期的な資産になる。

3. **デザインの意図はチーム全員とAIに届くべきだ**
   デザイナーの決定がエンジニアに伝わらず、AIにも伝わらないまま実装されることで品質が失われる。ドキュメントが橋渡しになる。

4. **新しいデザインプロセスを提案することが私たちの役割だ**
   既存ツールの不満を解消するだけでなく、AI開発時代に合ったプロセスのスタンダードをつくる。

### Values（価値観）

_プロダクトが大切にする言葉_

| 言葉 | 意味 |
|------|------|
| **Clarity（明瞭さ）** | デザインの意図が誰にでも・AIにも正確に伝わること |
| **Continuity（継続性）** | ツールが変わっても、デザインシステムは生き続けること |
| **Bridge（橋渡し）** | デザイナー・エンジニア・AI・ステークホルダーをつなぐこと |
| **Standard（新基準）** | 既存の常識を疑い、AI時代のプロセスを定義すること |
| **Trust（信頼）** | AIが迷わず実装できるほど、情報が正確で構造的であること |

### Personality（人格）

_このプロダクトが人だったら、どんな人物か_

**プロフェッショナルでイノベーター。ADHDで、集中したら止まらない静かな熱量がある。**

- 饒舌ではないが、話し始めると止まらない
- 業界の常識に疑問を持ち、次の時代の構造を先に作っている
- 自分の仕事に確信があるので、声高に主張しない。使えばわかると知っている
- 集中を妨げるものを本能的に嫌う。UIも、言葉も、無駄がない

### Tone of Voice（話し方）

_ユーザーへの語りかけ方。UIテキスト・エラー・オンボーディングの言葉に反映される。_

**「迷わせない。言い切る。次を示す。」**

Personalityの3要素がそのままToVの根拠になる：

| 根拠 | UIへの反映 |
|------|-----------|
| ADHD・集中が止まらない | 読む量を最小化。説明より「やること」だけを示す |
| 静かな熱量 | 「〜かもしれません」ではなく「〜です」と言い切る。迷いのない言葉 |
| プロフェッショナル | 馴れ馴れしくない。でも冷たくもない。信頼できる同僚の距離感 |
| イノベーター | 定型文を使わない。エラーは責めず、次の行動だけを示す |

**言葉の原則**

- 1文を短く。接続詞を減らす
- 受け身を避ける（「保存されました」→「保存しました」）
- エラーは原因より解決策を先に書く
- 空状態はユーザーを責めず、最初の一歩を示す
- 日本語・英語どちらでも同じトーンを維持する

**例**

| 場面 | 悪い例 | 良い例 |
|------|--------|--------|
| 保存完了 | 「データが正常に保存されました」 | 「保存しました」 |
| エラー | 「エラーが発生しました。再度お試しください」 | 「接続できませんでした。もう一度試す」 |
| 空状態 | 「コンポーネントがありません」 | 「最初のコンポーネントを追加する」 |
| 削除確認 | 「本当に削除してもよろしいですか？」 | 「削除しますか？　元に戻せません」 |

## Visual Identity（VI）

> **「どう見えるか」**
> MIを視覚言語に翻訳したもの。色・字・形・空間がMIと一貫していること。

### 設計思想

3つの参照が1つの原則に収束する。

```
バウハウス          ル・コルビジュ        アレグザンダー
「機能だけ残す」    「比例で設計する」     「生命が宿る構造をルール化する」
        ↓                 ↓                     ↓
              合理的だが、冷たくない
              数学的だが、息をしている
              構造的だが、有機的に成長できる
```

**原則: 「すべての要素は導出される。恣意的に決めない。」**

アレグザンダーの **Centers（中心性）** をデザインシステムに適用する。
コンポーネントは単体で成立するのではなく、互いを強め合う中心として設計される。
Button は Form と Label と Input が互いを支えることで初めて完成する。

## Behavior Identity（BI）

> **「どう動くか・どう応えるか」**
> ユーザーの操作に対してプロダクトがどう振る舞うかの原則。MIの人格がインタラクションに現れる。

### Motion Principles

**メタファー: 精密な機械時計**

カチッと決まる。予測できる。無駄がない。
バウハウスが優位。アレグザンダーの有機性は「減衰の自然さ」だけに残す。
バウンスしない。揺れない。迷わない。

**4原則**

```
1. 理由がなければ動かさない
   装飾のためのアニメーションは存在しない
   「なぜ動くか」を説明できないなら削除する

2. 動くなら素早く決める
   ユーザーの次のアクションを待たせない
   長い演出より即時の応答

3. 入場より退場を速く
   現れるものは丁寧に、消えるものは素早く
   注意を引くのは入場。退場は邪魔をしない

4. 動きは状態の変化を伝える手段
   「どこから来てどこへ行くか」を示す
   驚かせるためではなく、理解させるために動く
```

**Easing（イージング）**

```
Standard   cubic-bezier(0.4, 0.0, 0.2, 1)   汎用。素早く出て、スムーズに止まる
Enter      cubic-bezier(0.0, 0.0, 0.2, 1)   即座に動き出し、自然に減衰
Exit       cubic-bezier(0.4, 0.0, 1.0, 1)   素早く、迷いなく消える
```

バウンス・スプリング・オーバーシュートは使用しない。
時計の針はバウンスしない。

**Duration（デュレーション）**

```
instant    0ms    チェックボックス・トグルのON/OFF（即時）
micro     80ms    色・背景の変化（hover）
fast     120ms    小要素の出現・消滅（Badge・Chip・Tooltip）
default  160ms    標準（Button・Input・Dropdown）
slow     240ms    大きな要素（Modal・Drawer・Panel）
```

160msを超えたら疑う。240msを超えてはならない。

**動かさないもの**

```
- テキストコンテンツそのもの
- ページレイアウトの骨格
- ユーザーが集中して作業中の要素
- すでに表示されている静止コンテンツ
```

### Interaction Patterns

**Hover**

```
変化させるもの   背景色・テキスト色・ボーダー色
変化させないもの Transform（移動・拡大・浮き上がり）
Duration        80ms / Standard easing
```

カードやボタンを hover で「浮かせない」。
浮かせると「触れるもの」の印象になり、プロフェッショナルな密度感が失われる。
色の変化だけで十分に応答を伝えられる。

**Focus**

```
スタイル    2px solid Accent (#2563EB)
Offset     2px
Duration   即時（0ms）
```

フォーカスは即時に現れる。アニメーションしない。
キーボード操作時のみ表示（`:focus-visible`）。
クリック時は表示しない。

**Active / Press**

```
Transform   scale(0.98)
Duration    即時（0ms）→ 離した瞬間 120ms / Standard で戻る
```

押した感触を scale で表現する。
色変化と組み合わせて物理的な応答を伝える。

**Disabled**

```
Opacity     0.4
Cursor      not-allowed
Hover       反応しない（背景色変化なし）
```

**Loading**

```
種類        Skeleton（構造を保持） / Spinner（独立した処理）
Skeleton    opacity を 0.4 → 0.7 でパルス（1.5s / ease-in-out / infinite）
Spinner     回転のみ。16px または 20px。120ms/回転
```

Skeletonはレイアウトの崩れを防ぐために使う。
「何かが来る」という構造を先に示す。

**Toast / Feedback**

```
Enter   下から 8px スライドイン + fade-in   160ms / Enter easing
Exit    fade-out のみ                       120ms / Exit easing
位置    画面右下（デスクトップ）/ 画面下中央（モバイル）
自動消去 Success: 3000ms / Error: 手動で閉じる
```

エラーは自動で消さない。ユーザーが読んで閉じるまで残す。

**Dropdown / Menu**

```
Enter   origin から scale(0.95)→(1.0) + fade-in   120ms / Enter easing
Exit    fade-out のみ                               80ms / Exit easing
Origin  トリガー要素の端から展開する
```

### Error & Empty States

**エラー**

```
トーン    原因より解決策を先に書く（ToV原則）
粒度      フォームエラーはフィールド直下に表示。ページ全体のエラーはToast
責任      ユーザーを責めない。システムの問題はシステムが認める
```

**空状態**

```
哲学      空であることは失敗ではなく、始まりの状態
表示内容  最初の一歩を1つだけ示す。選択肢を並べない
アイコン  必要なら使うが、イラストや装飾的な絵は使わない
```

### Accessibility

```
コントラスト   WCAG 2.1 AA 準拠（通常テキスト 4.5:1 以上）
キーボード     全インタラクションをキーボードで操作できる
フォーカス     :focus-visible で視覚的に明確に示す
スクリーンリーダー  aria-label / role / aria-live を適切に使用
モーション     prefers-reduced-motion を尊重。Durationを0msにフォールバック
```
